# Write-up: Author Support and Communication Portal

How I approached it. The brief describes two very different users sharing one system. An author is usually worried about money or a date and wants a clear answer without chasing anyone. The support team spends its day inside a queue and needs to move fast without making mistakes. So the ticket became the centre of the design, and the book and royalty data became read only context that sits next to the ticket and makes it answerable. I kept the login identity in its own table, separate from the author records in the dataset, so access always comes from the signed token and never from an id the browser sends. The stack is React and TypeScript on the front, Express and TypeScript behind it, Prisma over SQLite locally and PostgreSQL in production. Nothing exotic, because whoever maintains this after me should be able to open any file and know what it does.

What I built first. The author side came first, on the real dataset: the books page with every field shown as it is, including the two in production books whose MRP and royalty rate are null in BookLeaf's own data (the page says so rather than filling in a plausible number), then query submission, then the thread that updates on its own when a reply lands. The admin side followed: a queue filtered by status, category, priority and date, sorted with urgent and longest waiting tickets at the top; a workspace where the AI's category and priority can be overridden, with the override recorded as a person's decision; internal notes that the author's API never returns, which is enforced in the queries and covered by a test; and replies that always start from a draft a person edits and sends. Around that, one error format for the whole API, validation on every input, and 34 automated tests.

The AI choices, and why. I tested before choosing. The brief's seven sample queries and a draft built from a real author's figures went through four models on three different routes. gpt-4o-mini took classification: best accuracy along with one other model, the cleanest JSON, roughly $0.00004 per ticket. Claude Haiku 4.5 took the drafts: it matched the tone of the brief's own sample replies best and was the only model that asked the author to confirm her bank details, as the brief's model answer does. A second round against the current flagships (GPT-5.5, Claude Opus, Gemini 3.1 Pro, Grok, Mistral Large, Qwen 3) changed neither pick. Under the app's real token budgets, 120 for classification and 600 for drafts, the reasoning models mostly spent the budget thinking and returned empty or cut off output. Testing also caught things I would have missed by guessing. Gemini 2.5 Flash spent its token budget on reasoning and returned truncated classifications and a stub draft at about twenty times the cost, so it went out. Haiku once invented a payout history that contradicted the figures it was given, so the prompt now forbids speculating beyond the supplied numbers. Two rules hold the design together. All policy facts live in one Knowledge Base module that the AI prompts and the fallback engine both read, so the two paths cannot disagree about the royalty cycle or the ₹1,000 threshold. And every AI call fails closed into a deterministic rules engine that scores 7 out of 7 on the brief's samples. If the provider is down or no key is configured, the portal still classifies, prioritises and drafts, and the queue labels those tickets as rules based instead of pretending otherwise.

Trade-offs I made knowingly. Server sent events with a polling fallback instead of WebSockets: simpler, and it survives proxies that kill long connections. Attachments are a form field only, which the brief allows; object storage with signed URLs is the production step. The event hub runs in one process; its publish and subscribe surface is small enough that Redis can replace it when the API needs more than one instance.

How this grows in production. PostgreSQL with migrations, Redis backed events, attachment storage with scanning, search and SLA timers with breach alerts on the queue, a follow up composer so authors can reopen a topic without starting over, and a few worked examples added to the classification prompt for the one case every model missed, the profile update that reads like a metadata issue but files as a general inquiry. The shape of all of that is already in the code. What I concentrated on for this assignment is the part authors and the support team touch every day, finished properly and tested.
